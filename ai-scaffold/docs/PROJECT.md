# Project

This file should become the central high-level description of the project.

Keep it concise and useful.

## Required Content

The completed `PROJECT.md` should normally contain:

### Executive Summary

A short summary of what is being built and the intended outcome.

### Description

Describe the project, its important functionality, and what the user requested.

Do not invent requirements that were not requested or reasonably implied.

### Purpose

Explain why the project exists and what problem it is intended to solve.

### References

Include relevant references supplied by the user when needed, such as:

* Existing projects
* Specifications
* Documentation
* Standards
* APIs
* Design references

Do not add references merely for completeness.

## Implementation Approach

Choose an implementation approach proportional to the size of the project.

For **small and straightforward projects**, prefer a one-shot approach:

`Understand → Implement → Validate → Finish`

Do not unnecessarily divide simple work into many phases or repeatedly stop for confirmation when the requirements are already clear.

For **larger or complex projects**, divide implementation into sensible phases or waves when this makes the work easier to manage.

For example:

`Foundation → Core Features → Integration → Polish → Validation`

Only introduce phases when they provide real value.

## General Rule

Prioritize the user's initial prompt and subsequent instructions.

Use the other files under `docs/` for detailed project rules, architecture, technology, security, structure, credentials, Git practices, and development processes.

The goal is to complete the project efficiently and correctly without unnecessary planning overhead, excessive ceremony, or wasted time.
